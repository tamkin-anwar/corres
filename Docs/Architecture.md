# Architecture and decisions

## ADR 001: Native iPhone foundation

Accepted: SwiftUI, iOS 17 minimum, Swift 6 concurrency, no third-party runtime dependencies. Native NavigationStack and TabView provide navigation semantics, safe areas, and platform behavior. The product uses its own surfaces and typography while preserving native controls. Core also builds as a small Swift package for tests. The Xcode app compiles the same Core sources directly; there is one implementation, not two copies.

Tradeoff: iOS 17 support constrains newer visual APIs. Prefer stable primitives and feature-gated enhancements over raising the minimum OS just for decoration. macOS and iPad-specific navigation are deferred.

## ADR 002: Provider-independent domain

Accepted: value types are Codable, Hashable, and Sendable. Thread identity is the pair of account and provider thread ID. Gmail data transfer objects, OAuth, persistence details, and inference outputs must not appear in SwiftUI views. MailRepository is asynchronous and Sendable. Actor isolation serializes sample mutations. The main-actor observable store publishes UI state and applies changes only after repository acknowledgment.

Attention is not a provider label and not a read receipt. Needs You, Waiting, quiet, and handled are Corres states. V1 must preserve manual overrides with provenance and versioning; later incoming replies can suggest reopening a handled item, but must not silently rewrite a manual decision.

## ADR 003: Explicit preview boundary

Accepted: the composition root injects SampleMailRepository. It contains six fictional conversations, no credentials, no network code, and no durable mail cache. Sample attention changes are intentionally transient. Appearance and first-run preference are the only UserDefaults values. The privacy manifest declares that use. Production Gmail must be another implementation, not an accidental fallback from a failed sign-in to fabricated mail.

Sample reasons are editorial fixtures, not live classifications or generated summaries. Brief derives counts from repository state, using an explicit clock in Core. Due-in-24h excludes past deadlines and handled items. Overdue attention will receive its own treatment in the connected product.

## ADR 004: Local-first privacy boundary

Implemented (2026-09-21): `SwiftDataMailRepository` (`@ModelActor`, its own isolated `ModelContext` per the documented Swift 6 concurrency pattern: `ModelContainer` is Sendable, `ModelContext` and model objects are not) is the app's real repository, replacing the ephemeral `SampleMailRepository` at the composition root. `PersistedCorrespondence` is a separate `@Model` type; persistence details still never reach `Correspondence`, `MailStore`, or any view, matching ADR 002's boundary. A versioned schema (`CorresSchemaV1`) and an (currently empty-stages) `SchemaMigrationPlan` exist from the start, since retrofitting a migration plan after a real schema change has already shipped is the failure mode this exists to avoid. `MailStore.resetSampleData()` gives an explicit, user-triggered return to a clean state (Preferences → Reset Sample Data), today's stand-in for per-account deletion until real Gmail accounts exist to scope a purge to.

Single-row mutation, not a full re-fetch (2026-09-21): `MailStore.mutate` (backing every pin, snooze, and attention change, the single most frequent interaction in the app) re-fetched every thread in the mailbox from SwiftData after each change, just to find and refresh the one row that actually changed, even though the repository layer underneath was already doing an efficient single-row update (`fetchOne`, a `compositeID`-predicated fetch with `fetchLimit = 1`). `send()` right next to it already got this right (splices the one returned thread into the local array). `setAttention`/`setPinned`/`snooze` now return the updated `Correspondence`, matching `send`'s existing pattern, and `mutate` applies that one item to `threads` in place instead of re-fetching everything, found by auditing the app's hot paths for this class of avoidable work, not by guessing.

Sample-data purge (2026-09-21): a real, on-device bug, not a hypothetical. `seedIfNeeded` seeds fictional sample threads before any Gmail account connects, and nothing ever removed them once one did, so they stayed mixed into a connected account's real Brief/Needs You/Waiting counts and Mail rows indefinitely, alongside Brief's copy still unconditionally claiming "Fictional mail. No account connected." `MailRepository.deleteSampleData()` removes only `account == "sample"` threads, called once from Preferences' Connect Gmail action and once from `CorresApp`'s launch task (covers relaunching already connected); Brief/Mail header copy now reads the actual connection state instead of a hardcoded claim.

Not yet done: explicit on-disk file-protection class verification (iOS's sandbox default file protection applies automatically, but that has not been specifically checked against this store), and bounded caches. Attachments (both viewing/downloading and composing with a new one) shipped in Batches 19/21. Never put tokens or correspondence in UserDefaults, analytics, crash attachments, or application logs. Backup protection needs device verification before real mail is accepted.

Gmail OAuth (2026-09-21): `GoogleAuthService` (App layer) wraps GoogleSignIn-iOS, originally requesting `gmail.readonly` only; widened same-day to also request `gmail.send` once replying/forwarding could really send (see ADR 005). `gmail.modify` followed later (Batch 18) for Archive/Trash, the same incremental-scope pattern. The session itself (access/refresh tokens) is never represented as a value in Corres's own code; it lives entirely in GoogleSignIn's own Keychain-backed store, which already meets the "tokens belong in Keychain, device-only accessibility" requirement without a second, parallel implementation to get right. `GmailAccount` (Core) carries only the signed-in email for UI purposes.

**Revised (2026-09-23, Batch 29): the "tokens live entirely in GoogleSignIn's own store" stance above no longer holds**, and the reversal was deliberate, not accidental drift. GoogleSignIn-iOS has no first-party API for more than one simultaneously-persisted account: `GIDSignIn.sharedInstance.currentUser`/`restorePreviousSignIn()`/`signOut()` all operate on one Keychain-backed slot (confirmed against google/GoogleSignIn-iOS issue #311, an open feature request, before building around it rather than assuming). True simultaneous multi-account, requested explicitly ("full sim multi account"), is not reachable through that single slot at all. `GoogleTokenProvider` (new, an `actor`) now captures each account's own OAuth refresh token (`GIDGoogleUser.refreshToken.tokenString`, a documented public property, extracted once at the moment that account signs in) into its own Keychain entry (`Keychain.swift`, a minimal `SecItemAdd`/`SecItemCopyMatching`/`SecItemDelete` wrapper, `kSecAttrAccessibleAfterFirstUnlock` so background push/BGAppRefreshTask can still mint tokens), and mints access tokens for any connected account directly against `https://oauth2.googleapis.com/token`, independent of whichever account happens to be GoogleSignIn's own current session. This is the same workaround pattern other apps needing true Google multi-account sign-in have documented; not a novel or unverified approach. `GoogleAuthService.signIn()` still drives GoogleSignIn's interactive consent UI (needed for the OAuth dance itself and the account picker), but every subsequent Gmail API call (`GmailAPIClient`, now taking an explicit `account:` on every method) goes through `GoogleTokenProvider`, never `GIDSignIn.sharedInstance.currentUser` again. A one-time migration (`GoogleAuthService.migrateLegacySingleAccountIfPresent`) reads whatever GoogleSignIn's own single-slot store still remembers on first launch after this update and captures its refresh token into the new storage, so an already-connected person's real connection carries over rather than silently requiring a fresh sign-in.

Multi-account scopes requested upfront now, not incrementally (2026-09-23, Batch 29): `gmail.modify` moves from Batch 18's incremental "ask only when Archive/Trash is first attempted" pattern into the same upfront `gmailScopes` array as `readonly`/`send`. Incremental scope requests need a live `GIDGoogleUser` object for the specific account being asked, which this design only ever has for whichever account GoogleSignIn's session currently holds mid-interactive-flow, not for every connected account afterward; requesting everything at connect time (one consent screen, same as before, just one more checkbox on it) sidesteps needing that entirely for every account connected from now on.

Archive and Trash (2026-09-22, Batch 18): until this, Corres could view and reply, but never actually manage a mailbox: no way to archive or delete a conversation at all, a real gap between it and a usable daily-driver mail client. `GmailAPIClient.modifyThread` (Gmail's `users.threads.modify`, removing the `INBOX` label) and `trashThread` (Gmail's dedicated `users.threads.trash` endpoint, distinct from `modify`) are the two new calls; both need `gmail.modify`, requested incrementally via `GoogleAuthService.ensureModifyScope()` (refactored `ensureSendScope`'s body into a shared `ensureScope(_:)` rather than duplicating the same three lines). `MailRepository.remove(_:)` is the new, provider-agnostic Core primitive both actions end with: an unconditional single-thread delete, used identically whether or not there was a real Gmail call first. `ThreadActionService` (new App-layer type, same shape as `OutboxService`) is where the two meet: for a real (non-sample) thread, the Gmail call is attempted first, and only on success does the thread disappear locally, the same "network before any local state change" rule `OutboxService` already follows for sending; a sample thread (no Gmail account) skips straight to the local remove. Wired into both `CorrespondenceList`'s swipe actions (trailing edge, Archive first since SwiftUI triggers whichever action is listed first on a full swipe, deliberately not Trash, given the trust this batch is trying to build) and `ConversationView`'s action bar; leaving a conversation via either one now also dismisses back to the list rather than showing "Conversation unavailable" as a dead end.

Email content still overfilling the screen, fixed for real this time (2026-09-22, Batch 22): reported directly against a real marketing email (a Disney+ "You May Also Like" promo) whose hero image and headline rendered enormous, overflowing well past the screen edge, exactly the class of bug Batch 14's "hard guarantee against horizontal scroll" was supposed to have already closed. Two real, independent causes, both fixed:
1. **Measurement race.** `HTMLMessageBody.Coordinator` computed its shrink-to-fit scale exactly once, in `didFinish`, from `document.body.scrollWidth/scrollHeight`. Real marketing HTML routinely finishes its main-frame navigation before every image has actually finished loading (a slow remote asset, or a CSS `background-image`, which doesn't reliably gate `didFinish` the same way a plain `<img src>` does): measuring once, right then, freezes the shrink scale and the SwiftUI-reported height against a page that then grows taller/wider a moment later, which from the outside looks exactly like "email content overfilling the screen." Now re-measures twice more, at 350ms and 1000ms after the first pass (a `loadGeneration` counter, bumped on every fresh `loadHTMLString` call, lets a re-measurement scheduled for an earlier, possibly-pooled-and-reused webview recognize it's stale and bail out rather than stomping a different conversation's correct size).
2. **A sender's own embedded viewport tag.** `html` here is only ever a message's body fragment, but WebKit's parser still finds and honors a `<meta name="viewport">` tag wherever it appears in the document, even one accidentally left inside a sender's body content by whatever template built their email (common boilerplate). Since `wrap()` appends its own `width=1024` viewport tag after the sender's content, a stray sender tag could silently win, and once `device-width` wins instead of the intended desktop-style width, any element the sender's template sized in fixed pixels (not a percentage) for a real mail client overflows that narrower containing block outright. Any such tag is now stripped from the sender's HTML before `wrap()` adds its own.

Composing with attachments (2026-09-22, Batch 21): the other half of viewing/downloading attachments (Batch 19), closing the gap flagged as deliberately out of scope there. `Draft.attachments: [PendingAttachment]` (new, `Codable`, so it rides through the durable outbox's existing JSON-encoded persistence for free, the same choice `PersistedOutboxEntry`/`PersistedCorrespondence` already made for `Draft`/`[MailAttachment]`) holds picked-but-not-yet-sent files entirely in memory; a `Draft.maxAttachmentsBytes` cap (25 MB, Gmail's own real limit) is enforced in `ComposeView` at pick time, not discovered later as a send failure after the person already waited through the undo window. `ComposeView` offers two pickers behind a paperclip toolbar menu: `PhotosPicker` (Photos framework, images only) and `.fileImporter` (any file type, including the security-scoped-URL access/read dance Apple's contract requires). `GmailMessageComposer.compose` gained an `attachments` parameter: with none, the message is exactly the single-part plain-text body it always was; with any, it becomes a real `multipart/mixed` RFC 2045 message (one text/plain part, one part per attachment, base64-encoded with proper 76-character line folding via `Data`'s own `.lineLength76Characters` option, which does nothing on its own without also passing an end-line option, verified with a standalone script before shipping). Trade-off worth naming: attachment bytes travel through SwiftData's JSON-blob outbox column exactly like everything else in `Draft`, which is simple and correct at the sizes this supports, but is not a design meant to scale past that; a real blob store would be the fix if that ever mattered.

Accessibility audit (2026-09-23, Batch 28): the first pass possible all session, since real-device testing only just started working (VoiceOver/Dynamic Type/Reduce Motion cannot be meaningfully evaluated any other way). Researched current SwiftUI accessibility guidance first, then swept the codebase against it rather than guessing at gaps. Found the existing code already fairly disciplined: every icon-only button already carries an explicit `.accessibilityLabel`, no `.onTapGesture` anti-pattern exists anywhere (everything uses real `Button`, which VoiceOver already understands), and `BriefView`/`WelcomeView` already adapt their layout at accessibility Dynamic Type sizes (`typeSize.isAccessibilitySize`) and cap hero text growth respectively. Two genuine, fixable gaps found:
- **Reduce Motion not respected.** `CorresShell`'s outbox banner (Undo/Retry/Discard) slid up from the bottom on an unconditional `.animation`/`.transition`, regardless of the person's Reduce Motion setting. Fixed by reading `@Environment(\.accessibilityReduceMotion)` and dropping the animation/slide-transition specifically when it's on, while keeping a plain opacity fade so the banner's appearance/disappearance doesn't become a jarring instant swap either (Reduce Motion's own guidance targets large-scale positional movement specifically, not all animation).
- **Two toolbar buttons missing the 44×44 minimum tap target** every other icon button in the app already declares explicitly (`ConversationView`'s previous/next conversation chevrons only had the *containing* `HStack` sized, not each button individually).

Deliberately not claimed as a complete accessibility pass: VoiceOver rotor navigation, live Dynamic Type behavior at true maximum accessibility sizes, and Increase Contrast have not been walked through on a real device with those settings actually enabled, only audited at the source level. That remaining verification is in Docs/Verification.md.

Plain replies rendering at a fraction of their intended size, fixed (2026-09-23): reported on the very same real message right after the dark-mode fix above was confirmed working, so a real, immediate regression from `wrap()`'s own design to catch, not a hypothetical. Root cause: forcing `<meta name="viewport" content="width=1024">` unconditionally (built to fix wide marketing HTML overflow, Batches 14/22) meant a block-level `<body>` with no explicit width of its own fills that 1024pt containing block regardless of how little text is actually inside it, so `document.body.scrollWidth` measured ~1024 even for two lines of plain-text reply, and `measureAndScale`'s shrink-to-fit math (correctly reacting to what looked like real overflow) divided the whole page, font size included, down to a fraction of its intended size for content that never needed to shrink at all. Switched to the standard `width=device-width, initial-scale=1`. Checked carefully that this doesn't regress the original wide-HTML fix, since that's exactly the failure mode this whole design exists to prevent: it doesn't, and is actually *more* accurate for that case too, not just neutral. Under the old fixed `width=1024`, `scrollWidth` measured `body`'s own box (1024), not the actual widest element, so even an ordinary ~600-650px marketing template was being over-shrunk against an artificial round-number baseline, just not obviously enough for anyone to have flagged it. Under `device-width`, `scrollWidth` now reflects the true content extent either way: no artificial overflow for plain text (scale stays 1), and a more precisely-computed shrink for genuinely wide content (measured against its real width, not 1024).

Two real on-device bugs, found the moment push actually worked (2026-09-23): reported directly after the first real end-to-end test of Batch 25/27's push relay (a real reply from a real sender arrived immediately, confirming the whole chain works). Two genuine bugs surfaced by real use, not by any build/test pass:
1. **HTML mail rendered nearly unreadable in dark mode, and the first fix didn't actually hold.** `WKWebView` has no knowledge of the app's own light/dark mode on its own; the first attempt set `webView.overrideUserInterfaceStyle` from `@Environment(\.colorScheme)` and relied on the CSS keyword `-apple-system-label` to pick that up. Reported still broken on a real device after that shipped: the keyword's resolution inside an offline `loadHTMLString` page (no real origin) didn't reliably track `overrideUserInterfaceStyle` the way assumed. Replaced with the standards-based mechanism actually documented to respect it: an explicit `@media (prefers-color-scheme: dark)` block with real hex color pairs, not a system keyword. Marked `!important`, deliberately: real mail HTML (Gmail's own quoted-reply markup included) routinely sets its own inline `color` on individual elements, which otherwise wins over a plain `body` rule regardless of dark mode; an `!important` author rule is the one thing in CSS's cascade that outranks a non-important inline style regardless of that inline style's own specificity (verified against the CSS Cascade spec, not assumed). `overrideUserInterfaceStyle` is still set (needed for the media query to match the app's actual appearance, not just the device's system-wide one), just no longer the *only* thing standing between the fix and the actual rendered color. Also swept the rest of the app for the same class of bug (hardcoded, non-adaptive colors): the only other hardcoded `Color(hex:)` uses are the Brief hero card and the brand "sculpture" mark, both deliberately fixed decorative elements paired with their own fixed backgrounds, not a readability regression.
2. **No recipient autocomplete in Compose.** Typing a "To" address required spelling out the full email every time, unlike Gmail or Apple Mail. `ComposeView.knownContacts` (new) builds suggestions from `store.threads`, deduped by sender email and ordered by most recent correspondence first, matching Gmail's own recency-weighted behavior; `toSuggestions` filters that list against what's typed (name or email, case-insensitive) and only shows while the "To" field is actually focused and editable. Scoped honestly: this is who has ever emailed *me* (real data Corres already has), not a real contacts book; someone only ever emailed *to* who never replied has no record to suggest from, a real, named limitation rather than a silent one.

AppDelegate now owns the app's services; background push/refresh fixed for real (2026-09-23, Batch 27): building `BGAppRefreshTask` renewal for the push watch subscription surfaced a deeper, pre-existing correctness gap in the design two entries below: `onDeviceToken`/`onRemoteNotification` were plain closures, wired onto `AppDelegate` from `CorresApp`'s own `.task`, which only reliably runs once the app's UI actually appears. That is not guaranteed for a background-only launch, the exact case both a silent push and a background refresh task exist to handle: if iOS fully terminates Corres between launches (common) and later wakes it purely in the background, SwiftUI's `WindowGroup` content view may never actually get instantiated into a live window, and a `.task` modifier on it may never fire. Both closures could then be `nil` precisely when the background handler needed them, meaning push delivery risked silently doing nothing in exactly the "app wasn't running" case that matters most.

Fixed by moving ownership: `AppDelegate` now directly owns `store`/`sync`/`auth`/`outbox`/`threadActions`/`labelDirectory`/`pushService` (constructed in its own `init()`, which runs before `CorresApp`'s `body` is ever evaluated) and performs the entire account-dependent launch sequence itself (`performLaunchWork()`, called from `application(_:didFinishLaunchingWithOptions:)`, which fires for every launch, background or foreground alike) rather than depending on SwiftUI's view lifecycle for any of it. `CorresApp` shrank to reading these straight off `appDelegate` and doing only genuinely foreground-only setup (`WKWebViewPool.shared.prewarm()`) in its own `.task`. This works cleanly with `@Observable` (not `ObservableObject`): a `View`'s body tracks whichever `@Observable` properties it actually reads during evaluation regardless of who allocated or owns the instance, so `CorresShell` re-rendering on `store`/`sync`/etc. changes needed no special wiring, just no longer needing `@State` ownership at the `App` level.

`BGAppRefreshTask` (new): registered in `didFinishLaunchingWithOptions` (registering even one async tick late is a documented source of silent failures where iOS never runs the task at all), identifier declared in `Info.plist`'s `BGTaskSchedulerPermittedIdentifiers` and the `UIBackgroundModes` `fetch` entry added alongside the existing `remote-notification` one. Renews the Gmail watch subscription (`PushNotificationService.renewWatch`) opportunistically, roughly every 4 hours at the earliest, resubmitting itself after every run since a submitted `BGAppRefreshTaskRequest` is consumed the moment it executes. Named honestly per the research behind this: iOS decides the actual timing based on its own usage/battery/thermal model, this is a real improvement over "renews only when the app happens to be opened," not a guarantee of punctual daily renewal, and it cannot be tested in Simulator at all, only on a real device.

Push relay deployed, and the missing notification itself, fixed (2026-09-23): the relay described below shipped and was deployed for real (`corres-509320` on GCP; verified end-to-end with `curl` before wiring the app: `/register` writes to Firestore, `/pubsub` correctly routes a real Pub/Sub-shaped payload). Asked directly whether Corres now delivers mail as fast as Gmail's own app; checking the actual code to answer honestly surfaced a real, significant gap: `AppDelegate.onRemoteNotification` synced new mail into local storage on every silent push, but never told the person it had arrived: no banner, no sound, nothing, defeating the entire point of turning notifications on. Fixed: `CorresApp`'s launch task now snapshots `{threadID: isUnread}` before each sync-triggered-by-push, and after syncing, diffs against the new state to find threads that are genuinely newly unread (not just "still unread from before," which would re-notify on every unrelated change) and Screener-approved (a pending/blocked sender's first message doesn't belong in a notification any more than it belongs in ordinary browsing). `PushNotificationService.notifyAboutNewMail(_:)` posts one real `UNNotificationRequest` with sender/subject for those, capped at a single notification per wake regardless of how many threads changed (a person who hasn't opened Corres in a while could have dozens land in one sync; one notification per message is exactly the kind of thing that gets a mail app's notifications turned back off, not the "as fast as Gmail" feeling actually being asked for).

Wide multi-column marketing HTML "breaking up" instead of reflowing, root-caused against real rendering-technique research (2026-09-23, immediately after the reliability/immersion fix above): reported with a direct screenshot-by-screenshot comparison against Apple Mail rendering the identical real email (the same UNIQLO one), specifically its two-column product grid: Apple Mail split it evenly, edge to edge, no gap; Corres rendered one column full-width and pushed the second column off the right edge of the screen. Researched how Apple Mail, Gmail, Spark, and Superhuman actually solve this before patching anything, rather than tweaking the existing JS-measure-then-zoom approach again: the documented, industry-standard technique real mail clients use is CSS-level, not view-level — inject stylesheet rules that force `table`/`img` to `max-width: 100%`, so WebKit's own native table-layout algorithm reflows a fixed-pixel-column desktop grid to the actual viewport width immediately and correctly, rather than measuring the rendered width via JavaScript after the fact and applying a `UIScrollView.zoomScale` transform to the whole page (`HTMLMessageBody`'s existing `measureAndScale`). That JS-measure-then-zoom approach is a real, known-fragile technique (confirmed via research: `shrink-to-fit` viewport behavior stopped working reliably in WKWebView after iOS 9.3, which is exactly why this workaround existed at all) and doesn't reliably catch a multi-column table whose real width only becomes accurate once real images finish loading asynchronously after the initial measurement — precisely the failure mode reported.

`wrap()`'s stylesheet now forces `table`/`td`/`th` to `max-width: 100% !important` and `img` to `max-width: 100% !important; height: auto !important`, matching the real technique (a sender's own `width` HTML attribute, not just a CSS property, needs `!important` in the stylesheet to reliably win). This is a native CSS reflow, not a JS-measured guess: a fixed 2-column table whose combined column widths exceed the viewport now has WebKit itself proportionally shrink both columns to fit, preserving their 50/50 split exactly the way Apple Mail's own rendering does, immediately, with no timing dependency on when images finish loading. `measureAndScale`'s JS-measured zoom stays in place as a backstop for whatever this CSS-level fix doesn't catch (unbreakable long text, for instance), but should rarely need to actually shrink anything for ordinary marketing HTML now that width overflow is handled at the CSS layer first.

Real, reported reliability bug: HTML mail silently clipped mid-content (2026-09-23): reported directly against a real, image-heavy marketing email (UNIQLO's own promotional mail), contrasted screenshot-by-screenshot against Apple Mail's own rendering of the same message, alongside the broader observation that Corres "feels like a wrapper for reading emails," not a full, native reading surface the way Apple Mail's own message view does. Two separate, real causes addressed:
1. **The clip itself.** `HTMLMessageBody`'s shrink-to-fit height measurement (`Coordinator.didFinish`) re-measured on a *fixed* schedule: once immediately, then again at 350ms and 1000ms, a guess from Batch 22's own fix for a narrower version of this same class of bug. `WKWebViewPool` deliberately disables the webview's own internal scrolling (`scrollView.isScrollEnabled = false`, by design: content is meant to scroll as part of the surrounding conversation, not in a nested scroll region), which means anything that finishes loading *after* that final 1000ms measurement — routine for a marketing email with dozens of real product images, especially over a slower real connection — grows the actual rendered page past the height SwiftUI allocated for it, and since the webview can't scroll to reveal that overflow, it is simply, invisibly clipped. Exactly what "the content just stops mid-way" looks like from the outside. Fixed by replacing the fixed 3-pass schedule with adaptive polling (`Coordinator.pollUntilStable`): checks at a steadily widening interval (150ms up to 2.5s per step) until two consecutive height measurements agree within a point (nothing left to load) or a ~10-second safety cap is reached. A short plain-text reply still settles after its very first check, same as before; a genuinely slow, image-heavy email keeps checking instead of giving up at an arbitrary fixed point.
2. **The "wrapper" feeling.** Two real, fixable causes, both about screen real estate ConversationView was giving up for no functional reason. First: the main app's own tab bar (Brief/Needs You/Waiting/Mail) stayed visible while reading a single conversation, stacking directly against ConversationView's own action bar below it — SwiftUI's default for a view pushed onto a `NavigationStack` inside a `TabView`, never explicitly overridden. Apple Mail's own message view is never double-chromed like this. `ConversationView` now sets `.toolbar(.hidden, for: .tabBar)`, giving the message the whole screen the same way Mail does. Second: the action bar itself was a flat, opaque, edge-to-edge `HStack` (`.background(.bar)`), where Apple Mail's own bottom toolbar is a translucent, inset capsule floating a short margin above the safe area. Restyled to match: `.ultraThinMaterial` in a `Capsule()`, inset from both edges, with a thin stroke outline (needed since a translucent pill floating directly over busy image content otherwise has no visible edge of its own).

Not a complete answer to the larger ambition stated alongside this report — "build the best, most elegant, functional email client on the market, with a lot of preferences so people can tailor it to themselves" — which is a real, ongoing product direction (Apple Mail's own reading surface as the immersion baseline, then Corres's own preferences/customization layered on top of it) rather than something one bug-fix pass closes. This entry is the reliability fix plus the most direct, concretely-diagnosable chrome gap; a dedicated preferences/customization batch is still ahead of it.

Multi-account performance sweep (2026-09-23, immediately after Batch 29 shipped): asked directly to make sure the just-shipped batch was as fast as possible, so audited it specifically rather than the whole app. Found a real, consistent pattern: every place Batch 29 introduced "do this for each connected account" had been written as a plain sequential loop, meaning someone with three connected accounts waited three times as long as someone with one for the same operation to finish, for no real reason, since each account's work is a fully independent network round trip. Fixed by switching each to `withTaskGroup`: `GmailSyncService.syncAll` and `.search`, `PushNotificationService.renewWatch`, `.disableAll`, and `.didRegister` all now fire their per-account work concurrently rather than one after another (`LabelDirectory.refreshIfConnected` already did this correctly when it shipped last batch). `AppDelegate.performLaunchWork` itself was restructured with `async let` so that `store.load()`/`auth.restoreConnectedAccounts()` (fully independent of each other) and `sync.syncAll`/`labelDirectory.refreshIfConnected`/`pushService.renewWatch` (three more independent network operations that used to run one after another purely because they were written in sequence, not because anything actually depended on it) now overlap; only what genuinely depends on the sync having finished (the second `store.load()`, `deleteSampleDataIfPresent`, `outbox.resumeAfterRelaunch`) still waits for it.

Parallelizing those, though, surfaced a real second-order cost worth catching before it shipped: with `sync`/`labelDirectory`/`pushService` now all starting at once, all three can ask `GoogleTokenProvider` for the *same* account's access token at the same moment on a cold cache (true at every launch, since the cache is empty then), and each would have independently noticed no valid cached token and fired its own refresh-token POST to Google, three real network calls and three hits against Google's OAuth endpoint for what should be one. `GoogleTokenProvider.accessToken(for:)` now tracks one in-flight refresh `Task` per account; a caller that arrives while that account's refresh is already running awaits the same `Task` instead of starting a second one, closing the gap the parallelization itself opened rather than leaving it as a new, unmeasured inefficiency.

True simultaneous multi-account, with both a unified and a per-account view (2026-09-23, Batch 29): requested explicitly, with a specific reference point given directly: "full sim multi account but also option to have an account switcher... do research on how to best implement and what apple mail gmail and spark superhuman does." Researched before designing anything. Apple Mail's "All Inboxes" and Gmail mobile's "All inboxes" both merge every account into one chronological timeline; the meaningful distinction found is that many apps claiming a "unified inbox" actually mean accounts stacked with a switcher, not a genuinely single merged timeline. Spark implements a real unified inbox (its Smart Inbox categorizes across accounts, not per account). Superhuman deliberately does *not* have a unified inbox at all, using only an account-switcher (Ctrl+1/2/3) to view one account at a time. Corres's own instruction asked for both, not a choice between them, so both shipped as real view modes over the same data, not two separate features: `CorresShell`'s new `accountFilter: String?` (nil = unified, a specific email = that one account only) is read by both `BriefView` and `CorrespondenceList`, filtering `store.threads` by `ThreadID.account`. This needed zero Core changes: every thread has always carried its owning account (`ThreadID.account`, ADR 002's own thread-identity design, from before multi-account existed), so "which accounts are merged into this view" was already a filter waiting to be used, not new domain modeling. An account-switcher menu (toolbar, only shown once a second account is actually connected — matching Superhuman's own switcher only mattering with more than one account) toggles between them; disconnecting the account currently being viewed falls back to the unified view rather than silently showing nothing.

A brand-new compose with more than one account connected needed a real answer for which account it sends *as*: `Draft.fromAccount` (new, optional, `Codable` so it survives the durable outbox's existing JSON persistence for free) is set from `ComposeView`'s new "From" picker, shown only for a new message when more than one account is connected — a reply/forward never shows it, since which account to send as is already fixed by which thread it belongs to (`threadID.account`). `OutboxService.resolveSendingAccount` encodes that precedence explicitly.

Push, per-account: `PushNotificationService` moved from a single `enable(account:)`/`disable(account:)` to `enableAll`/`disableAll` (one toggle for every connected account; there's no real reason to want new-mail pushes from one connected account but not another) plus a narrower `disable(account:)` for disconnecting a single account without touching the others. The relay's own Firestore schema had to change to actually support this correctly, not just the client: `Server/push-relay`'s `devices` collection mapped one device token to exactly one `emailAddress`; registering a second account with the same device token would have silently overwritten the first account's mapping, breaking push for whichever account registered first. Changed to `emailAddresses` (an array, `arrayUnion`/`arrayRemove` on register/unregister, `array-contains` on the Pub/Sub lookup) and redeployed to the same live function (`corres-509320`/`corres-push-relay`), verified with `curl` against `/register`/`/unregister` after deploying.

Push notifications (2026-09-22, Batch 25): researched directly before building anything, since the real constraint here is architectural, not a preference. Gmail's own push mechanism (`users.watch` + Google Cloud Pub/Sub) only ever delivers to an HTTPS server you own; there is no client-only path. Apple's own push API is private and iCloud-only, so a third-party mail client cannot use it the way Apple Mail does. That means real push unavoidably needs a two-hop relay: Gmail → a server (via Pub/Sub) → APNs → the device. Weighed directly against staying fully backend-less (`BGAppRefreshTask`, opportunistically scheduled by iOS, commonly 15 minutes to several hours late) versus building the minimal relay that could do the job; chose to build it, since near-real-time notification is close to table-stakes for what "premium mail app" means to people, and the relay can be made content-blind, which meaningfully changes the privacy calculus versus a naive design.

`Server/push-relay` (new, separate from the iOS app, a small Node.js Google Cloud Function) is that relay, and it is deliberately as dumb as it can be:
- It never sees message content in either direction. Gmail's Pub/Sub notification for a mailbox change carries only `{ emailAddress, historyId }`, never subject/sender/body; what this relay forwards on is a silent APNs push (`content-available` only, no alert text), so the actual mail a person sees is fetched and rendered entirely on-device by an ordinary sync, exactly like any other sync already works.
- It never receives a Gmail OAuth token. The **client** calls `users.watch` (via `GmailAPIClient.watch(topicName:)`, using the token it already holds for every other Gmail call), naming the relay's own Pub/Sub topic as the target. The relay only needs a Firestore mapping of `{ deviceToken → emailAddress }` to route the eventual contentless ping to the right device; it never needs, stores, or could use a person's Gmail credentials.
- APNs auth uses a provider auth key (ES256 JWT, hand-signed with Node's built-in `crypto` module rather than adding a JWT dependency for something this small; verified correct against the public key with a standalone script before committing), not a device certificate, avoiding a second expiring-artifact renewal problem on top of Gmail's own.
- `Server/push-relay/README.md` documents the one-time GCP + Apple Developer setup this needs; none of that can be done from inside this repo (it needs the studio's own cloud/developer accounts), so the deployed relay's URL and Pub/Sub topic name are committed as placeholders in `PushNotificationService` until that setup is actually done, the same "fails closed on unconfigured infrastructure" pattern the rest of the app already follows.

Client side: `PushNotificationService` (new App-layer `@Observable`) is Preferences-toggle-driven, not requested at launch (an unprompted permission dialog is exactly the kind of thing this session has otherwise been trying to remove, not add). `AppDelegate` (new, minimal, wired via `@UIApplicationDelegateAdaptor`) is a thin bridge for the two callbacks SwiftUI's `App` protocol has no equivalent for (the real APNs device token arriving, and a silent background push arriving); it holds no state of its own and is wired with closures from `CorresApp`'s own launch task, since the delegate is constructed before `store`/`sync`/`auth`/`pushService` exist. Known, accepted gap: `users.watch` expires after about 7 days and this only renews it at app launch, not via a background task, so an account left unopened for a week silently stops getting push until the next open (see the README).

Real on-device migration crash, fixed (2026-09-22, hotfix after Batch 25): reported directly against a real device with real, already-synced mail: the app kept losing its local store on every launch (`CoreData: error: Cannot migrate store in-place: Validation error missing attribute values on mandatory destination attribute`, entity `PersistedCorrespondence`, attribute `attachmentsData`). Root cause: `attachmentsData`, `isUnread`, and `labelIds` (Batches 19/23/24) were added to `PersistedCorrespondence` as non-optional properties with no inline `= <default>` literal. SwiftData's automatic lightweight migration needs that literal to backfill existing on-disk rows that predate the column; without one, migrating a real, already-populated store fails outright, while a fresh install never exercises migration at all and looked completely fine in every build-and-test pass this session. `CorresApp.makeModelContainer()`'s existing catch-and-fall-back-to-in-memory path caught the resulting error, so this wasn't a hard crash, but a silent one: local state (pins, snoozes, the Screener's decisions, everything) reset to a fresh in-memory store every single launch, invisible from a compile-and-domain-test pass and only found because the actual device logs were shared directly. Fixed by adding the missing default literals; also audited every other non-optional property added mid-session for the same gap and fixed two more found the same way (`senderDecisionRaw`, defaulted to `.approved` to match `isInitialSync`'s existing "already-in-the-inbox" rule, and `imagesTrusted`, defaulted to `false`) before they could cause the identical crash on a future release. `PersistedOutboxEntry` was confirmed unaffected: it's a whole separate entity added wholesale in Batch 10, not new columns on an existing one, so it never had a backfill problem to begin with. Lesson for every future `@Model` property addition: it needs its own default literal, full stop, unless it's genuinely part of the very first shipped schema.

Gmail labels (2026-09-22, Batch 24): the last line of "Corres still cannot label or otherwise modify anything else in your real mailbox," closed. `Correspondence.labelIds: [String]` (new) carries a thread's raw Gmail label ids exactly as `labelIds` arrives on the message resource, unfiltered (system ids like INBOX/UNREAD/SENT/CATEGORY_* are mixed in, since a per-message resource carries no type info to tell a real user label apart from one of Gmail's own, only the separate labels catalog does), deliberately just an opaque provider id, the same treatment `latestMessageID`/`messageIdHeader` already get, rather than inventing a richer Core type for something only the App layer can actually interpret. `GmailAPIClient.fetchUserLabels()` (new) is the one place that distinction is made, filtering Gmail's labels catalog (`users.labels.list`) to `type: "user"` only. `LabelDirectory` (new App-layer `@Observable`, refreshed once after launch/sync) is the id-to-name lookup everything else reads from. `ThreadActionService.toggleLabel(_:isOn:for:)` reuses the established Gmail-call-then-local-change shape via the shared `modifyThread` endpoint (no new Gmail call needed, add/removeLabelIds already generalized enough); its local step recomputes the thread's full label set from whatever is already known locally rather than trusting a possibly-stale copy, since another toggle could race ahead of it. `MailRepository.setLabelIds(_:for:)` (new) is the Core primitive that lands it. Unlike `isUnread`, `upsert`'s in-place update always takes `labelIds` from the incoming message regardless of `preserveAttention`/who sent it: labels are genuine Gmail mailbox-organization state, not a triage decision Corres invented, so there's no "our own sent copy shouldn't downgrade it" concern the way there is for attention. `ConversationView` shows a thread's known user labels as chips (filtered through `LabelDirectory`, so system ids never leak into the display) and a "Labels" menu in the action bar to toggle any of them; both are hidden entirely when no account is connected or the directory hasn't loaded any labels yet, rather than showing an empty, confusing menu.

Manual read/unread (2026-09-22, Batch 23): `Correspondence.isUnread` (new, genuinely separate from `attention`; see its doc comment) is seeded from Gmail's `UNREAD` label at sync time exactly like `attention`/`reason` already were, but a manual toggle afterward is its own fact from then on, the same "stops following Gmail's state the moment a person decides for themselves" rule `attention` already followed. `ThreadActionService.setUnread(_:for:)` reuses Archive/Trash's exact Gmail-call-then-local-change shape (its `perform` helper generalized to take a `local` completion closure instead of hardcoding `store.remove`), toggling the same `UNREAD` label `modifyThread` already supports rather than needing a new Gmail endpoint. `upsert` in both repositories carries `isUnread` through the same `preserveAttention` branch attention/reason already use: a genuine inbound message updates it, our own sent copy reappearing never does. `ConversationView` auto-marks a thread read the moment it's opened (`.task(id: currentID)`), matching what every real mail client already does; the explicit toggle is unaffected by this since `.task(id:)` only reruns when the conversation being viewed actually changes, not on every store mutation. `CorrespondenceRow` gained an unread dot + bold sender name; `CorrespondenceList` gained a leading swipe action alongside Needs You/Pin.

Server-side search (2026-09-22, Batch 20): local search (`MailQuery.filter`) only ever searched `MailStore.threads`, which only ever holds what has already synced (the first sync caps at a couple hundred messages, see Batch 4's incremental sync note), so searching for anything older silently found nothing, exactly the "my own mail app can't find my email" moment that erodes trust rather than building it. `GmailAPIClient.searchMessages(query:account:)` reaches Gmail's own search (`q=`, its full query syntax, not a client-side substring match) for up to 25 results. `GmailSyncService.search(_:account:)` is the App-layer entry point: debounced 450ms after typing pauses (`CorrespondenceList`'s `.task(id: search)`, cancelled automatically by SwiftUI if the person keeps typing), silent on failure (a network hiccup mid-keystroke does not deserve the same error banner a failed full sync does), and merges any matches through the exact same `repository.upsert` every ordinary sync already uses, so a found result becomes real local mail going forward, not a one-off shown-then-forgotten result. `MailStore.refresh()` (new) is a lighter sibling of `load()`: re-fetches `threads` without touching `state`, since `load()`'s `state = .loading` would otherwise flash the whole list away to a spinner on every debounced search tick, a real regression the first implementation of this had and caught before shipping. A small `Searching Gmail…` indicator in the list header, tied to `GmailSyncService.isSearchingRemote`, gives visible feedback that a search is genuinely reaching past what's synced rather than quietly coming up empty.

Viewing and downloading attachments (2026-09-22, Batch 19): the other half of the same audit that found Archive/Trash missing. `Correspondence.attachments: [MailAttachment]` carries what's attached (filename, MIME type, size, Gmail's own `attachmentId`) but never the bytes: attachment content is fetched on demand, a single `GmailAPIClient.fetchAttachmentData(messageId:attachmentId:)` call (Gmail's dedicated `users.messages.attachments.get`, since attachment bytes are omitted from the ordinary `users.messages.get` response), the same "collapsed by default, load on request" instinct already applied to remote images. `GmailAPIClient.map`'s new `collectAttachments` walks the message's MIME part tree the same way `collectCIDParts`/`inlineCIDImages` already did, and deliberately excludes any part carrying a `Content-ID` header: those are inline images `inlineCIDImages` already renders directly in the HTML body, and without this exclusion every embedded logo or signature image would also show up a second time as a downloadable attachment underneath. Stored as one JSON-encoded column on `PersistedCorrespondence` (`attachmentsData`), the same choice `PersistedOutboxEntry.draftData` already made for `Draft`: no query ever needs to filter by attachment, so one column beats several. In `ConversationView`, tapping an attachment downloads it to a temp file and hands it to iOS's own QuickLook preview (`.quickLookPreview`), which already has save/share built into its own toolbar, rather than Corres inventing a parallel one. Composing a message with a newly-attached file was not built this batch; that needs a file/photo picker and a multipart MIME encoder on the send path, a separate, larger piece of work.

Gmail calls should run directly from device where possible. No Corres server should retain message bodies by default. A future push relay should carry minimal account routing and wake-up information, not readable correspondence. Do not claim end-to-end encrypted email: ordinary Gmail transport does not provide that property.

Cloud AI is a separate opt-in processing path with purpose, provider, retention, and revocation disclosure. Mail contents are untrusted data, never instructions authorizing tools or sending. Suggestions must link to source evidence. No autonomous sending, clicking, payment, or calendar changes based on mail content.

## ADR 005: Gmail sync and mutation reliability

First pass (2026-09-21): `GmailAPIClient` (App layer) fetched a fixed 25 most recent INBOX messages via `users.messages.list` + `users.messages.get?format=full`, parses headers/MIME body (depth-first search for the first `text/plain` part, falling back to the snippet), and maps to `Correspondence`. One-way only (no read/label writes back to Gmail) remains true; `upsert` only ever inserts threads not already present, a real message's content is immutable once received, so there is nothing to "update," and an existing thread's manual attention/pin/snooze is never touched regardless of what a later fetch of the same thread would say (ADR 002).

History-cursor incremental sync (2026-09-21): replaced the fixed window. The first sync per account (and any sync after a stored cursor is rejected as expired) does a paginated full listing capped at 200 messages per label, then reads the account's current `historyId` from `users.getProfile`. Every sync after that calls `users.history.list?startHistoryId=...&historyTypes=messageAdded&labelId=...`, fetching only messages added since the stored cursor, and advances the cursor to the response's `historyId`. Gmail documents this pattern, including the expired-cursor 404, in its [sync guide](https://developers.google.com/workspace/gmail/api/guides/sync); `GmailAPIClient.ClientError.historyExpired` is that specific signal, and `GmailSyncService` catches it and falls back to a full resync automatically rather than surfacing an error. The cursor itself lives in `UserDefaults` inside `GmailSyncService` (App layer), keyed by account email, not in the SwiftData schema: it is a Gmail sync-mechanics detail, and keeping it there matches ADR 002's boundary between Core domain and provider specifics. Disconnecting an account and Preferences' "Reset Sample Data" both clear the stored cursor, since either one can delete already-synced local threads that an incremental sync would otherwise never re-fetch.

Sent-mail sync (2026-09-21): both listing and history calls now run once per label (`INBOX`, `SENT`), merged before fetching full message content, since Gmail's `messages.list`/`history.list` `labelId`/`labelIds` filters are AND-scoped (there is no single-call OR query for "either label"), so a genuine OR needs two calls. Closes the real gap where a thread living only in Sent (you started it, no inbound reply has synced yet) was invisible; `GmailAPIClient.newerHistoryId` compares the two label queries' returned `historyId` numerically, not lexicographically ("100" sorts before "99" as strings), since Gmail's `historyId` is one whole-mailbox counter and the two per-label queries should normally agree but are compared safely in case they ever don't.

Concurrent message fetch (2026-09-21): `fetchMessages` used to await one `users.messages.get` call after another, sequentially, for every id a listing/history call returned; a full sync (up to 200 messages per label, two labels) meant a couple hundred real network round trips back to back, the actual dominant cause of a sync feeling slow, not anything about SwiftUI. Replaced with a bounded-concurrency `TaskGroup` (8 requests in flight at once, not unbounded, to stay reasonable against Gmail's per-user rate limits), verified against a standalone 237-item simulation for correctness (every id fetched exactly once, no duplicates or drops) before touching the real client. Gmail's batch HTTP endpoint (bundling many calls into one multipart/mixed request) would reduce round trips further still; considered and not adopted here, since it needs manual multipart response parsing with no first-party Swift support, for a smaller incremental win over the bounded-`TaskGroup` fix at meaningfully higher implementation risk.

Reply-sync fix (2026-09-22): the limitation noted above (and previously left open) is fixed. Real-world symptom: a user emailed someone through Corres, they replied, and the reply never appeared, because `upsert` had never touched an already-known thread, full stop, so a genuinely new message in an existing thread (a real reply, or the first real content arriving behind `OutboxService`'s local placeholder) was silently dropped forever. `Correspondence` gained `latestMessageID` (the individual Gmail message id behind whatever this thread is currently showing, distinct from `id.providerID`, which is the thread id and never changes); `GmailAPIClient.map` now carries the message's own `id` into it. `upsert` in both repositories now compares an incoming item's `latestMessageID` against the already-known thread's: identical means "the same message came back again," a no-op exactly as before; different means a genuinely new message arrived, and the thread's content is updated in place (subject/body/htmlBody/sender/messageIdHeader/receivedAt), while pin/snooze/Screener decision/image trust are never touched either way. A `receivedAt`-ordering guard (`item.receivedAt >= existing.receivedAt`) makes this correct even when a single sync batch contains more than one new message for the same thread in either order (e.g. our own sent copy and the recipient's reply both landing since the last sync), so the thread always ends up reflecting whichever message is actually newest. One more distinction was needed: our own sent copy showing back up in a later Sent-label sync (`item.senderEmail == item.id.account`) updates content but deliberately does not touch attention/reason, since Gmail reporting our own sent mail as "read" must never downgrade a thread still legitimately Waiting; a genuine inbound message (anyone else) updates both, which is what correctly flips a thread back to Needs You when a reply actually arrives.

Cursor/upsert ordering (2026-09-21, verified rather than changed): `GmailSyncService.syncIfConnected` writes the cursor to `UserDefaults` only after `upsert` (SwiftData) succeeds, not before, and stays that way rather than being made transactionally atomic. True atomicity would mean moving the cursor into the SwiftData schema so both writes share one transaction, reversing this ADR's own choice to keep Gmail sync mechanics out of the Core domain (see above). The actual risk this ordering avoids is real data loss, not merely redundancy: writing the cursor *before* upsert would mean a crash between the two advances the cursor past messages that were never actually saved, and the next sync would never re-fetch them (permanent silent loss). Writing it *after*, as today, means a crash between the two only risks re-fetching and re-upserting messages that already made it in, which `upsert` already treats as a no-op. Not pursuing full cross-store atomicity for a failure mode that is already benign, not dangerous, is the deliberate decision here, not an oversight.

Sending (2026-09-21): replying, replying all, and forwarding to an existing, real (non-sample) synced thread now really send, via `users.messages.send` with a `raw` RFC 5322 message (`GmailMessageComposer`, App layer) and the thread's Gmail `threadId`. Correct Gmail threading needs three things to agree: the request's `threadId`, `In-Reply-To`/`References` headers matching the parent message's real `Message-ID`, and a matching `Subject`. So `Correspondence.messageIdHeader` now carries that header through from sync, and `Correspondence.senderEmail` carries the sender's actual address (a reply's "To" is not safe to build from the display name `sender` alone). Scope widened from `gmail.readonly` to also request `gmail.send`; both are Google's "sensitive," not "restricted," scopes (a standard OAuth consent-screen review before general release, no CASA security assessment required). An account connected before this shipped only has `gmail.readonly` granted, so `GoogleAuthService.ensureSendScope()` requests `gmail.send` incrementally, the first time it's actually needed, rather than forcing a disconnect/reconnect.

Brand-new compose sending (2026-09-21): a from-scratch message (no reply-to thread) now also sends via Gmail whenever an account is connected, closing the gap this ADR previously left open. It has no existing `threadId` or parent `Message-ID` to echo back, so `GmailAPIClient.send` is called with `threadId: nil` and `GmailMessageComposer.compose(inReplyTo: nil)`; Gmail assigns the new message its own thread and returns that thread's real id in the send response, which `GmailAPIClient.send` now returns to its caller. `OutboxService` uses that returned id to file the local record under `ThreadID(account: <real account>, providerID: <Gmail's real thread id>)` instead of a locally-invented UUID, via a new `realThreadID` parameter threaded through `MailStore.send` and `MailRepository.send`; a later sync of that same thread then recognizes it as already-known (matches on the real id) rather than inserting a duplicate. Only a genuinely local-only send (no account connected) still falls back to a synthesized "sample"-account id.

`OutboxService` (App layer) makes Send feel instant rather than making the person wait on a network round trip: ComposeView dismisses immediately when Send is tapped, and the real work (a Gmail API call, when applicable, then local bookkeeping) happens after a short undo window, the pattern real premium mail clients use (queue optimistically, offer undo, don't block on a confirmation prompt or a spinner). The Gmail call happens *before* any local state changes, not after: on failure, nothing here claims the message went out, and the failed draft surfaces through `OutboxService.failed` with Retry/Discard rather than a thread silently sitting in "Waiting" for a reply that was never sent.

Durable outbox (2026-09-21): closed. `MailRepository` gained `outboxEntries`/`saveOutboxEntry`/`removeOutboxEntry`, backed by `PersistedOutboxEntry` (SwiftData, Core layer; the `Draft` itself is stored as one JSON-encoded column, not five separate ones, since nothing ever queries by draft subject/body at the persistence layer, unlike `PersistedCorrespondence`'s columns, which genuinely earn their keep). `OutboxService.queueSend` persists a `.pending` `OutboxRecord` before the undo-window timer even starts, not after; `commit` removes it on success or rewrites it `.failed` on a real Gmail error. `OutboxService.resumeAfterRelaunch()`, called once from `CorresApp`'s launch `.task` after `store.load()` (needed to re-resolve a resumed reply's source thread from its `threadID`), restores whatever the outbox still held from before the app last quit: a `.pending` entry means the app was force-quit before its undo window ever finished or was explicitly cancelled, so the safest resolution is to finish sending it now (there is no window left to re-offer undo for); a `.failed` entry is restored so its Retry/Discard banner reappears rather than the earlier failure silently vanishing.

Also fixed while rewriting this: queueing a second send while a first was still mid-undo-window used to only cancel the first's timer `Task`, which made it return early without ever calling `commit`, silently dropping the first draft entirely, contradicting the code's own comment claiming it "commits immediately." `OutboxService` now keeps the superseded draft/thread alongside `pending` specifically so it can actually be committed for real when superseded, not just cancelled.

Bounded retries with backoff and jitter (2026-09-23, Batch 26): closed, honestly scoped. Researched current practice first (exponential backoff alone can synchronize retries across a burst of failures from the same outage; jitter is what actually spreads them). `OutboxService.sendViaGmailWithRetry` gives a failed send up to 3 attempts total, with exponential backoff (2s, 4s, 8s base) plus up to 50% random jitter on top, before falling through to the existing `.failed`/Retry-Discard UI, not instead of it. Retries only fire for failures where the request almost certainly never completed on Gmail's side: a connection-level failure before any response arrived (`URLError` cases like `.timedOut`/`.networkConnectionLost`/`.notConnectedToInternet`), or Gmail's own response explicitly saying "try again" (429, or any 5xx, now distinguishable because `GmailAPIClient.ClientError.badResponse` gained a `statusCode`, previously discarded). Any other 4xx fails immediately: Gmail has already processed and explicitly rejected the request, and retrying only repeats the identical rejection. Named honestly rather than oversold: Gmail's send endpoint has no idempotency-key mechanism of its own (unlike Stripe-style APIs), so there is no way to guarantee a retry can never double-send; restricting retries to genuinely transient-or-ambiguous failures is the bounded version of safety actually available, not a claim of true exactly-once delivery. Per-account serialization, the other item on this list, turned out to already hold structurally on inspection rather than needing new code: `OutboxService` is `@MainActor`, `resumeAfterRelaunch` awaits each queued entry's `commit` one at a time instead of firing them concurrently, and `queueSend` already explicitly commits any still-pending send before starting a new one. Classification logic and backoff timing verified correct with a standalone script before committing (matching this session's own precedent for App-layer logic with no existing test seam, e.g. `GmailMessageComposer`'s MIME assembly).

Gmail scope selection and verification must be reviewed against the then-current [official scopes](https://developers.google.com/workspace/gmail/api/auth/scopes) and [Workspace data policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy). Device-first architecture is not a blanket exemption from Google's verification requirements.

## ADR 006: Safe rendering and accessibility

Accepted for sample bodies: plain native Text, no HTML or external resources.

Real mail (2026-09-21): `HTMLMessageBody` (WKWebView) renders a synced message's real HTML when present, plain Text fallback otherwise. Done: JavaScript is always disabled (`allowsContentJavaScript = false`); mail content is untrusted and never needs to execute code to display correctly; every link tap is intercepted and opened in the system browser rather than navigating inline, after validating the scheme is http/https (blocks a `javascript:` or arbitrary custom-scheme link from doing something unexpected on tap). Attachments are not handled at all yet (no attachments exist in the synced data).

Remote image blocking (2026-09-21): every `<img src="http(s)://...">` is rewritten to an inline transparent-pixel `data:` URI before the HTML reaches WKWebView, so no network request happens until the user taps a "Show Images" banner reporting the blocked count. `cid:`-referenced images are unaffected: `GmailAPIClient` already inlines those as `data:` URIs upstream, and the blocking regex only matches `http`/`https` sources, so real embedded content still renders while a same-shaped tracking pixel does not. Deliberately narrower than a `WKContentRuleList`: only `<img src>` is rewritten, not CSS `background-image` or other resource types, trading some coverage for much lower false-positive risk against arbitrary inline styles. Revisit if a real tracking pixel delivered via `background-image` is ever actually seen.

WKWebView pooling (2026-09-21, superseding the single-instance warm-up below): the remaining cost after warm-up, researched specifically rather than assumed: creating a fresh, un-pooled `WKWebView` is one of the heaviest actions an app can take on iOS, since each instance not sharing a `WKProcessPool` can spin up several of its own OS processes, and `HTMLMessageBody.makeUIView` created a fresh instance per conversation, never reused. `WKWebViewPool` (new file) holds a small shared pool (2 instances, one `WKProcessPool`); `makeUIView`/`dismantleUIView` borrow from and return to it, the same reuse-not-recreate pattern `UITableView` cell reuse uses, rather than one separate throwaway warm-up instance. Reuse pitfalls handled explicitly, each backed by research: navigation/UI delegates cleared on return to the pool (a stale delegate is otherwise still live and can fire callbacks at a coordinator that no longer owns the instance); scroll position and zoom-scale bounds reset on return (a previous email's shrink-to-fit scale would otherwise flash briefly on reuse, before the new content's own measurement corrects it); the webview is hidden (`alpha = 0`) from the start of a new load until `didFinish` (or any failure delegate, so it's never left permanently invisible), so a pooled instance never flashes its previous conversation's content for a frame. `configuration.suppressesIncrementalRendering = true` added too, a specific cited win for short HTML content. `CorresApp`'s launch task now calls `WKWebViewPool.shared.prewarm()`, pre-creating the pool itself instead of a separate throwaway instance.

WKWebView warm-up (2026-09-21, historical, now superseded by pooling above): a process's first WKWebView pays a measurable cold-start tax spinning up its out-of-process WebContent engine; the original fix created and retained one throwaway instance separate from real usage. Kept here for the record of what was tried first and why it wasn't sufficient on its own (real per-instance creation cost remained on every subsequent conversation, addressed by pooling instead).

No horizontal scroll, hard guarantee (2026-09-21): the uniform shrink-to-fit `zoomScale` (see the wrap()/didFinish entry above) already computes a scale meant to prevent this, and `scrollView.isScrollEnabled = false` already prevents scrolling regardless. Added `overflow-x: hidden` on `html`/`body` in the wrapping CSS as a backstop against any visual overflow surviving a scale miscalculation; `overflow` only clips rendering, it doesn't affect the `scrollWidth` measurement the scale calculation depends on, so it can't interfere with that logic, only add a second, independent safeguard on top of it.

Per-sender image trust (2026-09-21): weighed directly against Apple's Mail Privacy Protection, which pre-fetches every remote image through Apple's own relay servers at a randomized time, masking the real open time/IP from the sender entirely, so images always just show with zero tracking. That is a genuinely better user experience, but it is a real backend service, not a client feature: Corres would need to run and pay for its own image-proxying infrastructure at scale, directly contradicting the local-first, no-server architecture ADR 004 already established, and is not the right investment before the product has any users or revenue to justify it. `Correspondence.imagesTrusted`, propagated the same way `senderDecision` already is (stamped at insert time from any existing thread of that sender; see `upsert`'s doc comment, the mechanism is identical, just a different per-sender fact), is the smaller, no-infrastructure alternative: tapping "Show Images" once (`MailStore.trustSenderImages`) reveals that message and remembers the sender, so a newsletter already trusted never needs a repeat tap on its next issue. Deliberately one action, not a separate "always" control nobody asked for. Domain-tested in both repositories: trusting a sender flips an existing thread, and a later message from the same sender arrives already trusted.

Use semantic text styles, spoken control labels, minimum 44-point actions, a solid-surface fallback, and no color-only state. Custom navigation paths are decorative alongside native labels. Press motion respects [Reduce Motion](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducemotion). Real VoiceOver and large-text inspection are release gates, not claims inferred from compilation.

## ADR 007: The Screener

Accepted (2026-09-21), grounded in HEY's own documented Screener mechanics: a sender earns entry once, not per message. `Correspondence.senderDecision` (`pending`/`approved`/`blocked`, Core) is stamped at insert time in `MailRepository.upsert`, not tracked in a separate registry, so there is exactly one source of truth per thread and nothing to keep in sync: a sender's decision comes from whatever's already persisted for any of their earlier threads, defaulting to `.approved` when `isInitialSync` is true (an account's first sync, or any resync forced by an expired history cursor, both cases where every sender present is an established relationship, not a new arrival) and to `.pending` otherwise. `MailStore.approveSender`/`blockSender` call `MailRepository.setSenderDecision`, which cascades to every existing thread from that sender at once, matching the one-decision-per-sender model, not a per-thread toggle.

`MailQuery.filter` excludes `pending`/`blocked` threads from ordinary browsing (Brief, Needs You, Waiting, Mail) the same way it already excludes a snoozed thread, and for the same reason: still real mail, still recoverable, just not surfacing by default. An explicit search finds it regardless, mirroring the existing snooze precedent exactly rather than inventing a second rule. `ScreenerView` groups a person's `pending` threads by sender (one row per sender, not per message) for the approve/block decision; `BriefView` surfaces a "New Senders" entry point only when at least one is waiting.

Approving or blocking is entirely local to Corres; neither writes anything back to a real Gmail account (ADR 002/005), consistent with the read/reply-only scope Corres holds today.

## Planned production data flow

SwiftUI features -> main-actor store -> repository -> protected local database.

Gmail sync actor -> validated provider adapter -> database transaction -> observable snapshot. Outbox -> provider -> acknowledgment/reconciliation -> local state. Optional intelligence -> explicit processing policy -> source-linked suggestions. Views never call the network directly.
